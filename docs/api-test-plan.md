# API Test Plan: Issues API

These acceptance tests define expected API behavior. Run them against a disposable copy of `Backend/data/issues.json` so test requests do not alter the working seed data. Use `Backend/requests.http` for request examples.

All error responses should use this JSON envelope:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "A specific explanation of the problem."
  }
}
```

| Test | Request                                                                      | Expected result                                                                                                 |
| ---- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| T01  | `GET /api/issues` with issues stored                                         | `200 OK`; response is a JSON array.                                                                             |
| T02  | `POST /api/issues` with valid title, description, and priority               | `201 Created`; full issue returned with server-generated UUID `id`, `Open` status, and ISO 8601 `createdAt`.    |
| T03  | `POST /api/issues` without a title                                           | `400 Bad Request`; error code `VALIDATION_ERROR`.                                                               |
| T04  | `POST /api/issues` with priority `Critical`                                  | `400 Bad Request`; error code `VALIDATION_ERROR`.                                                               |
| T05  | `PATCH /api/issues/{id}/status` for an existing issue with status `Resolved` | `200 OK`; full updated issue returned with status `Resolved`.                                                   |
| T06  | `PATCH /api/issues/{id}/status` with status `Deleted`                        | `400 Bad Request`; error code `VALIDATION_ERROR`.                                                               |
| T07  | `PATCH /api/issues/ISS-999/status` with a valid status                       | `404 Not Found`; error code `ISSUE_NOT_FOUND`.                                                                  |
| T08  | `GET /api/issues` with an empty data file (`[]`)                             | `200 OK`; response is an empty JSON array, not an error.                                                        |
| T09  | `POST /api/issues` with extra `id`, `status`, or `createdAt` fields          | `201 Created`; returned server-owned values are generated by the API and do not use the client-supplied values. |
| T10  | `POST /api/issues` with a non-JSON content type                              | `415 Unsupported Media Type`; error code `UNSUPPORTED_MEDIA_TYPE`.                                              |
| T11  | `POST /api/issues` with malformed JSON and `Content-Type: application/json`  | `400 Bad Request`; error code `VALIDATION_ERROR`.                                                               |
| T12  | `POST /api/issues` with a request body larger than 1 MB                      | `413 Payload Too Large`; error code `PAYLOAD_TOO_LARGE`.                                                        |

Every error response includes both an error code and a message. The data file remains unchanged when validation or content-type checks fail.
